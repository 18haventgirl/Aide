# 笔记搜索：规模、故障与困难样例基线

日期：2026-10-01。接续工程收尾阶段；离线评估仅使用合成笔记，不读取或修改用户笔记，不调用 LLM。后续页面复验使用现有笔记进行只读搜索，没有新增、修改或删除用户数据。

## 规模与性能

使用固定版本本地 BGE、真实 Chroma、临时 SQLite。每组有两个模拟用户、两种标签、两种状态，10% 为长笔记；报告记录模型/权重版本、样本哈希与内存。建库后跑 75 次串行查询、25 次四并发查询。

模型加载另耗时约 5.32 秒。两组查询检查用户/标签/状态均未发现越界。四并发时部分查询按现有设计回退到关键词，不能把该延迟当作四个 BGE 推理同时执行。计时从工作线程内服务函数开始，不含任务排队、HTTP、鉴权、WebSocket、浏览器渲染。集合为临时内存 Chroma，不代表持久化 HNSW 冷启动、磁盘故障或多进程写入性能。样本大量复用主题，仅适合规模/延迟对照，不用于宣称语义召回率。

## 困难样例集

新增 `backend/tests/fixtures/note_search_contrast_v1.json`：12 条近似主题笔记，48 条正例问题、12 条负例，共 60 题。包括国内/境外报销、交租/退租、运动安排/场馆维修、纸书/电子备份、猫/狗照料、面试/项目会议，以及错别字和词面干扰。

每条笔记两问为开发集、两问为保留验证集，负例各半。保持此前距离阈值 **0.55**，本轮没有调整在线排序或门槛。文件哈希随报告保存。它仍由开发者结合合成资料编写，不是外部真实用户盲测；看过结果后，也应作为后续回归集，不能再称完全未见数据。

| 指标 | 开发集 | 保留验证集 |
| --- | ---: | ---: |
| Recall@5 | 24/24 | 24/24 |
| 无相关笔记拒绝 | 3/6 | 2/6 |

验证失败项：自行车链条的化学机理 → 运动安排；打印机卡纸维修 → 场馆维修；自由泳世界纪录 → 运动安排；外币防伪印刷 → 境外报销。

结论：该小集的正例可找到，但部分共同词会带回无关主题。旧集 10/10 负例拒绝来自较容易的负例，不能推断真实查询的误召回已经解决。逐通道复验确认：上述四个问题关闭向量后仍返回同一错误笔记，而独立 BGE 候选均为空；问题来自 FTS 的 OR 查询，只需共同词就进入融合结果，并无词法覆盖门槛。下一步离线比较词法覆盖门槛，保留完整字面匹配和独立向量通道；不能为抬高本集分数而修改负例标签。

## 故障与并发一致性

笔记专项测试现为 15 项，通过。新增三项有控制的故障注入：

1. embedding 正在执行时另一线程更新笔记：旧版本不发布，查询能读取新原文，后续索引任务处理最终版本。
2. 发布新索引后清理旧向量失败：任务保持可重试，重试可清理旧块。
3. 向量写入后以 `SystemExit` 模拟进程中断：保留未完成任务，模拟租约到期后新索引实例恢复，块 ID 不重复。

这些验证使用假 embedding/向量集合控制故障点。不是实际操作系统杀进程、断电、真实 Chroma 崩溃或真实网络断连测试，也没有验证跨进程长期租约续期。

## 词法误召回修复（同日后续）

在上述归因基础上，为 FTS 候选增加规则：同一块至少覆盖查询中一半的去重、去停用词后的词语。使用已保存的分词字段，不再为每个候选重复分词，不需要重建索引。OR 仍用于取候选；完整字面匹配直接保留，BGE 独立召回也不受此门槛限制。向量距离保持 0.55，没有针对漏例放宽。

| 冻结样例 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 困难开发集 Recall@5 / 负例拒绝 | 24/24、3/6 | 24/24、6/6 |
| 困难验证集 Recall@5 / 负例拒绝 | 24/24、2/6 | 23/24、6/6 |
| 原 v1 验证集 Recall@5 / 负例拒绝 | 19/20、10/10 | 19/20、10/10 |

明确的代价：`双休日的骑行计划记哪了` 不再命中运动安排，词法和独立 BGE 均为空。这是已知回归，保留样例和标签；不能说该策略没有漏召回。采用这一更保守的规则减少只有共同词的结果，后续用新表达评估语义召回或重排收益，不加针对该题的硬编码。同一开发者样例的前后对比不是新的外部盲测。

修复后困难验证查询 P95 为 30.7ms，原 v1 为 25.7ms；仅为本次小集服务函数耗时。上面的 100/1000 条规模数字来自修复前基线，未冒充新版本完整规模复测。新增三项词法/精确/语义通道回归后专项测试为 **18 项通过**。

对照报告：`contrast_coverage_v1.json`、`synthetic_coverage_v1.json`；命令仍使用 `--fixed-distance 0.55`，更改 `--output` 即可。基线 `contrast_v1.json` 保留。

实际页面复验：更新本项目 API/MCP 后，前端继续使用 3002，健康检查通过。使用现有笔记做只读搜索，字面查询返回一项，无关查询显示未找到，点击退出搜索恢复原三项列表。日志确认前者 `dense=completed, dense_candidates=1, results=1`（906ms），后者候选和结果均为 0（15ms）。第一次查询明显慢于温模型小集，不能以温模型 P95 代替冷启动体验。重启后旧页曾显示断开，刷新后已连接；仍未验收完整自动重连故障矩阵。

联合回归：协作路由、外部 MCP 所有权、笔记检索、医疗依据和答案审计共 **32 项通过**。既有 Pydantic 弃用提示仍存在，LiteLLM 价格表联网失败后使用内置备份，不代表生成 API 调用失败。

## 复现

在 backend 目录：

```powershell
.\.venv\python.exe -m service.services.note_search_benchmark --sizes 100 1000
.\.venv\python.exe -m service.services.note_search_evaluate --cases tests/fixtures/note_search_contrast_v1.json --fixed-distance 0.55 --output data/note_search_reports/contrast_v1.json
.\.venv\python.exe -m unittest tests.test_note_local_search
```

本地报告：`backend/data/note_search_reports/scale_v1.json` 与 `contrast_v1.json`。不进入 Git。benchmark 启动前至少要求 1536MiB 可用内存，建库每 50 条检查 768MiB 余量；不是固定内存占用承诺。评估脚本的 P95 已统一为 nearest-rank（向上取整）。
