# Aide 项目自检与简历评估

日期：2026-10-15。目标岗位：AI 应用 / Agent 开发。

2026-11-02 更新：下文前端检查数字为 10 月 15 日的基线。修复后的结果见[前端错误排查与验证记录](frontend-quality-validation-20261102.md)。

## 结论

可以写进简历，定位为可演示的个人 AI 应用项目。已有实际代码和验证支撑的亮点包括：Triage 与专员 Agent 编排、MCP 工具接入、混合检索及重排、病历多格式解析、字段来源校验、人工核对及幂等入库。

当前不能据此宣称生产级医疗平台、临床准确率、真实业务落地、大规模用户验证或自研模型。公开部署前应优先修复身份认证与管理接口授权。投递前最好补齐聊天入口到 Agent 工具的完整验收，并建立独立质量评测。

## 按优先级排列的问题

### P1：统一密码认证仍在生产模式生效

位置：`backend/core/auth_core/auth.py:179-207`；相关默认 JWT 配置位于同文件第 21 行。

`authenticate_user` 在判断本地演示开关前，先接受一个固定密码，再按用户名取得用户资料。关闭 `AIDE_ENABLE_LOCAL_TEST_LOGIN` 或设置 `NODE_ENV=production` 只会关闭快捷演示账号分支，不会关闭后续统一密码认证。知道有效用户名的人仍可能取得该用户身份。密码哈希相关依赖的存在不代表登录时实际检查了每个用户的密码。

隔离复现：生产模式、本地测试账号开关关闭，模拟目录返回一个普通用户后，固定测试密码仍认证成功。另有条件性配置风险：未设置 `JWT_SECRET_KEY` 时会使用源码内默认值；本轮没有断言当前运行服务正在使用默认密钥。

修复：真实账号采用逐用户密码哈希或外部身份提供方；演示认证整体限定在显式开发模式；生产启动时对缺失或示例 JWT 密钥直接报错。增加生产模式拒绝演示凭据、不同用户密码隔离的回归测试。

### P1：管理接口只有登录验证，缺少角色或资源授权

位置：`backend/api/websocket_api.py:1380-1463`；`backend/core/auth_core/middleware.py:123-160`。

`POST /broadcast` 接受任意已登录用户，可向全部连接、指定用户或房间发送署名为 `system` 的消息。`GET /connections` 返回全部连接信息，包含其他用户资料及连接 IP；`GET /rooms` 也未过滤私有房间。`CurrentUser` 只验证登录，且现有 `verify_user_permission` 无条件返回 `True`，直接换成 `AdminUser` 仍不足以修复。

隔离复现：普通用户依赖调用原始广播路由，HTTP 返回 200，模拟全站广播被调用且发送者为 `system`；连接列表可返回另一个虚构用户的信息。真实发送量为 0。

修复：实现有效的管理员权限检查，限制全局管理入口；普通用户接口按身份过滤自己的连接与房间，定向发送还需验证目标授权。为普通用户拒绝管理操作及跨用户访问补回归测试。

### P2：聊天任务缺少明确的并发上限

位置：`backend/api/websocket_api.py:988-1032`。

每条合法聊天消息都会直接创建后台任务。现有任务字典用于跟踪，未在该入口执行每用户或全局并发限制；声明的消息队列也没有在这里承担排队限流。连续发送消息可能同时启动多个模型任务，增加资源和费用压力。该结论来自代码审查，本轮未做收费模型压力测试，也未测定崩溃阈值。

修复：设置用户及全局并发上限、同会话任务策略、超时与取消、明确的繁忙反馈。病历解析已有每进程 2 个并发槽位，但它不覆盖普通聊天，也不能充当多实例的全局限流。

### P2：前端规范检查尚未达到可作为合并门槛的状态

位置：`ui/package.json` 的 `lint`；主要结果集中于 `ui/src/services/apiService.ts`、`ui/src/lib/api.ts`、`ui/src/pages/Dashboard.tsx` 等。

本次 ESLint 失败：121 个错误、12 个警告。其中 96 个为显式 `any`，21 个为未使用变量，3 个为组件热更新导出规则，1 个为未使用表达式；12 个警告为 Hooks 依赖检查。类型检查与生产构建通过，不能据此说代码规范检查也通过。这些检查结果不等同于 121 个已证实的运行故障。

病历解析的三个主要组件与 `medicalDocumentAPI.ts` 本次各为 0 错误、0 警告。整改应覆盖整体前端，优先处理 Hooks 行为风险及 API 类型，再清理其余问题；不建议靠全局关闭规则获得通过。

### P2：复现文档与测试入口存在实际不一致

位置：`README.md:147`、`ui/package.json:16`、`backend/requirements.txt`。

- README 仍要求 Node.js 16+，但当前安装的 Vite 7 要求 `^20.19.0 || >=22.12.0`，PDF.js 5.6.205 声明 `>=20.19.0 || >=22.13.0 || >=24`。照文档用 Node 16 无法保证构建。
- `test:ws` 指向 `ui/test-websocket.js`，当前文件不存在，因此该测试入口不可用。
- 本分支未发现已提交的 GitHub Actions 工作流。前端有锁文件；后端 Agent SDK、FastMCP、FastAPI 等关键依赖未完整锁定版本，尚无全新机器安装验证。

修复：统一并验证支持的 Node/Python 版本，修正失效测试入口，固定后端依赖，添加后端测试、前端检查与构建的 CI。OCR 测试应显式安装可选依赖及生成样本，避免关键格式矩阵被静默跳过。

## 尚未达到的验收与评测要求

这些是能力证据的缺口，应与上面的已确认代码问题区分。

1. **聊天完整链路**：已有独立 Runner 的真实模型验证，但之前预览环境没有启动完整 MCP 服务，并记录过聊天 WebSocket 重连错误。病历 HTTP 工作区通过，不能推导出“聊天 → Triage → 解析工具 → 工作区核对”的完整链路已验收。需要在依赖齐备的环境补测，并明确正常、断线与工具失败的行为。
2. **病历抽取质量**：8 种格式场景主要由同一份虚构门诊材料生成，另有首轮虚构出院小结验证。格式兼容测试不能替代跨模板的质量评测；没有真实脱敏病历、手写、模糊、倾斜和多栏的系统质量结论。已发现温度单位 OCR 误识别。
3. **Agent 成功率**：现有编排单测检查工具与 handoff 配置，不能证明自然语言路由、工具选择及任务完成率。建议构建覆盖单域、多域、歧义、失败和文档提示注入的固定题集，并保留未参与调试的测试集。
4. **RAG 指标边界**：已有 33 题冻结回归集报告，但失败项已用于修改规则，它不是独立盲测。Recall@5=1.000 是该题集的检索指标，不能表述为医学回答准确率。5,000 条华佗候选属于离线研究试验，未接入正式回答链路。
5. **运行指标与恢复**：现有检索耗时日志有价值；尚缺整条任务的稳定成功率、端到端 P50/P95、每份材料的 token/费用和长任务恢复证据。同步病历解析与每进程限流适合当前演示，多实例、持久队列与断点恢复没有验证。

下一轮病历质量评测建议使用 50–100 份公开合成或有授权的脱敏材料，覆盖门诊与出院、多模板与不同扫描质量，先定义姓名/日期精确匹配、过敏与否定/待排限定词保留、来源有效性、缺失值正确留空等指标。该数量是后续建议，当前尚未完成。

## 面向 AI 应用 / Agent 岗位的表述

### 可用的简历项目描述

**Aide：多 Agent 助手与病历结构化解析｜个人项目**

技术栈：Python、FastAPI、OpenAI Agents SDK、MCP、React/TypeScript、Chroma、BGE、RapidOCR。

- 基于 Triage 与专员 Agent 实现任务路由，结合 handoff、Agent 工具调用及 MCP 接入不同能力，将病历解析封装为独立专员并复用后端服务。
- 构建 BGE 向量检索与 BM25 关键词检索融合链路，使用加权 RRF 与交叉编码器重排，支持来源展示、索引状态过滤及重排失败降级。
- 实现 PDF、图片、DOCX、TXT 病历抽取，将模型字段与原文页码/行号关联，校验原文引用及否定、待排等限定词，通过人工修正与确认完成健康记录入库。
- 覆盖用户隔离、异常文件、虚构字段与并发重复确认等回归场景，并完成 6 种扩展名、8 种格式场景的上传、解析、核对、保存与重开验证。

描述的是项目事实。个人职责应按自己实际参与和掌握的部分调整，不写“独立从零研发 OCR/模型/Agent 框架”。KnowResume 的分层思路参考和重新实现范围已有文档，应保留来源说明。

### 面试前需要能解释的内容

1. 为什么某些请求交接给专员，另一些请求由 Triage 调用专员工具并汇总；两者如何影响上下文与结果整合。
2. 混合检索、RRF 和重排分别解决什么问题，如何用独立样例证明收益及发现退化。
3. 为什么模型给出的字段要与来源核对；丢失“否认/待排”为何危险；保守留空会带来什么召回代价。
4. 同时点击两次确认为何只生成一条健康记录；事务、条件更新与用户归属分别承担什么职责。
5. 当前哪些测试替换了模型、哪些真实调用了模型；通过格式测试与证明抽取质量有什么区别。
6. 认证和全局接口授权为何仍不适合公开部署，以及怎样验证修复有效。

## 建议推进顺序

1. 修复两类 P1 权限问题与默认密钥配置，增加对应回归，作为公开部署前置条件。
2. 在完整 MCP 环境验收聊天与解析 Agent 链路，修复失效测试入口，加入并发上限。
3. 清理前端检查、统一环境版本、固定依赖并加入 CI，让别人能够按文档复现。
4. 增加独立病历与 Agent 评测，记录成功率、耗时与费用；再把可复核指标写入简历。
5. 准备一段稳定演示：上传样例 → 来源定位 → 修正 → 保存 → 重开，并展示一个主动留空或失败降级案例。
