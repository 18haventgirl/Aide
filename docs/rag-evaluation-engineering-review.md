# RAG 待解决问题：原因调查、补救方案与工程验收标准

整理日期：2026-10-14。审计基线：`47db1e4`。诊断报告沿用首次启动时的 `20261010` 文件命名，本文不以文件名推定新的执行日期。

## 1. 明确判断

目前已经具备可追溯、可运行、能发现真实问题的研发评测基础；尚未达到完整的工程验收体系。没有统一的行业数字能定义“工程级”，这里按本项目的复现、输入一致、数据代表性、答案质量、性能故障和发布门槛判断。

已有证据：题集/语料哈希、模型 revision 与权重固定；四模式真实对照；指标契约测试；原始失败留存；独立 Chroma 实验；实际 MCP 与健康记忆样例闭环。仍缺：与最终证据预算一致的主指标、可定位原文片段的标签、独立验证集、答案/任务级评价、统计误差、并发故障性能、CI 门槛和新环境复现。

当前 suite 共 234 题：111 旧开发、33 旧回归、10 中文症状、80 新中文题。新 80 题已用于修复，v3 正确标为回归，不能作为新的未见集继续调参并声称泛化。41 项单元/契约测试、123 题混合检索回归和五次 MCP 探针属于不同证据，不相加成独立用户样本数。既有真实 LLM 演示不是系统性的答案评测。

## 2. 三个误过滤样例的直接原因

独立进程内重新同步同一 72 篇/95 块 corpus，使用同一真 BGE 模型、同一 query 和同一目标切片。三个目标均进入重排候选池，排除“这三例被候选配额挤掉”的假设。取实际 tokenizer 的未截断句对并定位关键句：

| 样例 | 主题 | 句对 token 数 | 关键句 token 位置（从 0 开始） | 256-token 分数 | 512-token 分数 |
| --- | --- | ---: | ---: | ---: | ---: |
| CGS024 | 防鼠设施/鼠夹 | 506 | 393 | .003245 | .916468 |
| CGS035 | 职业防护全程使用 | 418 | 372 | .008481 | .511898 |
| CGS042 | 果蔬/果汁替代关系 | 468 | 308 | .009711 | .942771 |

三段关键内容都在 256-token 边界之外。现有切片按 **600 字符、80 字符重叠**，索引文本额外包含标题和章节；重排的 tokenizer 将整个 query/passage 句对截到 256 tokens。检索返回正确长切片，交叉编码器却只看到前部内容。原有固定 `.05` 门槛随后把低分候选清空。

此前“低于阈值”的结论描述了过滤机制；本次确认更上游的输入截断是这三例的直接问题。否定问法、医学领域适配和分数校准仍值得研究，但不能继续把它们作为已确认的三例主因。

同一通用诊断问题与所有切片配对做 tokenizer 计数：95 个句对中 66 个超过 256、1 个超过 512，最大 513。这个比例来自固定诊断问法，不等于线上问题分布或 69.5% 的实际错误率；它说明长度不匹配具有较大影响范围。

手工取包含关键句的短原文范围，仍用 256 tokens，三例分数分别 .893272 / .369267 / .990914。**这些范围由已知正确答案定位，属于诊断上界，不是自动切片方案，也不能拿 3/3 宣称上线召回恢复。** 512-token 单段评分也没有执行全候选排序、阈值取舍或整套验收。

## 3. 重排与拒绝门槛的其他问题

首轮融合+重排 Recall@5=.953（61/64），无答案过滤 8/8；融合未重排 Recall@5=1.0（64/64），无答案过滤 6/8。另外 CGS043、CGS055、CGS056 的相关文档从第一名降到第二名，说明恢复三例后仍需检查排序质量。

现有 `.05` 是固定 sigmoid 分数门槛，没有利用本项目开发标签做校准。sigmoid 把模型 logit 映射到 0～1，并不会自动得到“有 5% 的医学可信度”或稳定的相关概率。官方 [FlagEmbedding encoder reranker 实现](https://github.com/FlagOpen/FlagEmbedding/blob/master/FlagEmbedding/inference/reranker/encoder_only/base.py)将 normalize 作为可选 sigmoid 操作，使用 token 预算、only_second 截断和按长度排序，值得沿用其处理方式。

降低 `.05` 有可能接受更多噪音，且无法补回模型没读到的文字；全量改成 512 虽能让这三段完整输入，仍会增加计算量、改变其他分数。应先修输入表示，再用独立开发数据比较排序与拒绝策略。

候选池还存在潜在扩容风险：24 dense + 24 lexical 合并后只选 8，固定保留 dense 前 5 与 lexical 前 3，当前没有报告正确证据在 union/重排池/最终上下文各阶段的保留率。这三例进入了池，但未来更多文档时不能假设配额始终够用。

## 4. CPU 耗时的调查

同一问题、同一组 8 个候选，CPU 2 线程、max_length=256，真实模型三次串行热运行：

| batch | 三次耗时 ms | 中位数 ms |
| --- | --- | ---: |
| 1 | 3464.59 / 2629.38 / 2473.10 | 2629.38 |
| 4 | 2447.70 / 2306.89 / 2433.63 | 2433.63 |
| 8 | 2316.80 / 2313.88 / 2226.25 | 2313.88 |

batch 8 的中位数比 batch 1 低约 12%，分数最大差约 2.51e-8。当前 CPU/输入下并没有 8 倍加速。与上轮整组 P95≈4.44秒属于不同测试条件和统计量，不能据此宣称整体 P95 已下降近一半。

本次按1→4→8执行，未随机化配置顺序，也未记录CPU频率和其他进程负载；这个小实验足以排除“改batch自然带来数倍加速”的预期，不足以直接选定生产配置。正式性能比较应交错/随机执行配置并记录运行条件。

进程峰值约 1198.5 MiB；单请求串行测量不能推算并发能力。模型推理锁串行化共享 CPU forward，用户并发会增加排队；还缺 queue_wait、tokenize、forward、候选长短、缓存命中、HTTP、LLM 等独立耗时。

优先实验：消除重复标题和无关长前缀；长度分桶；4/6/8 候选预算；CPU 线程 1/2/4；缩短用于重排的子块。之后才试 ONNX/OpenVINO，逐题比较排序变化和数值差异。[Sentence Transformers 官方性能指南](https://sbert.net/docs/cross_encoder/usage/efficiency.html)提供这些后端及量化路线；是否适合本机由实测决定，不能套用其公开机器数字。FP16 不作为当前 CPU 默认优化。

### 5.1 文档命中不能替代证据命中

当前 `evaluate()` 调用 `search(limit=20)`，把 chunk 的 doc_id 去重，然后取前 K 个文档。实际 MCP 默认为 `top_k=5` 个 chunks，LLM未必收到去重后的第五篇文档。更重要的是，命中了同一文章的另一段也算正确文档，关键依据可能完全没进 prompt。

旧数字作为**文档检索诊断指标**保留，不能全部当作用户实际得到的证据覆盖率。新增主要指标：在与工具一致的chunk/token预算下，目标原文范围是否保留；同时报告文档级指标。只通过调优返回数量来获得更高分应被合同测试阻止。

### 5.2 样本数量与独立性

72篇中66篇来自同一份健康素养释义 PDF，只有7个不同原文URL。新64正例为16个主题各4种问法，主题内相关；14个相关文档也出现在旧开发题中。字符相似度启发式审查未发现≥.8的近似问句，但不构成完整泄漏证明。检索测试共享同一corpus是正常做法；需要区分未见问法能力与新主题/来源泛化。

8/8无答案通过并不能证明可靠拒绝：即使假设独立样本，Wilson 95%下界仅约67.6%；4/4下界约51.0%。64/64下界约94.3%，61/64区间约87.1%～98.4%。这里仅解释小样本误差，主题相关时不能把这些区间直接当作可靠统计结论；正式对照应按主题聚类做 paired bootstrap，并保留逐题胜/负及分组指标。

四道紧急题只测试 `is_urgent` 规则，不包含足够正常反例，也不测模型回答、急症优先响应或等待检索时间。近期41项测试通过是软件合同证据，不能换算为医学效果。

### 5.3 其他需补齐的合同

- unanswerable/urgent标签禁止携带相互冲突的正例标签；全suite检查ID/问句重复并报告来源，不因老集共用ID无说明地混算。
- 参数、hash、资格、内存预算检查失败也形成结构化失败记录；目前一部分在report建立/try之前抛出。逐题异常必须保留，不能删除失败题再统计平均值。
- 冷模型、首查、热未缓存、缓存命中、scope gate、不检索的紧急规则分别统计；“去掉第一题”不能保证后面所有题都是同一热状态。
- runtime cache目前主要以query/preview/limit/collection_count为key。集合内容变了而数量不变时可能在TTL内返回旧内容；M3应绑定active_index_version/content_hash。
- 活跃集合直接sync不是完整staged切换；同一篇upsert后再删旧块不等于全库原子发布。同步中断/回滚需真实验证。

## 6. 按优先级实施的补救方案

本轮交付原因调查和设计，没有调整在线重排长度、阈值或知识库。以下均是待实现项和建议验收目标。

### P0-A：对齐主指标与最终证据合同

实现位置：`medical/evaluate.py`、`medical/experiment.py`、`mcp-serve/medical_tools.py`，新增 `medical/evaluation/metrics.py` 和 `evidence_contract.py`。

1. 统一 evidence_budget：默认5 chunks、明确token预算、每篇最多2块；检索实验、工具打包共用同一选择器。可调参数必须进入报告。
2. 旧文档级指标继续保留，新增 `evidence_span_recall_at_budget`、`context_precision`、`candidate_recall_union`、`candidate_recall_rerank_pool`、`critical_condition_retention`。
3. 新标签包含 `doc_id/version/body_hash + span_ranges + required_conditions`，范围针对规范原文body，禁止用变化后chunk_id作为唯一真值。角色、日期、禁忌和例外与主结论一起标注。
4. 每题保存候选阶段、原文范围、模型实际token截断、最终证据pack哈希与budget；同一trace能查到LLM收到的范围。
5. 导出 corpus/query/qrels/runfile，用 [BEIR评价实现](https://github.com/beir-cellar/beir/blob/main/beir/retrieval/evaluation.py) 对齐文档级指标；采用适合Windows的可选adapter，避免强制引入重依赖。BEIR不负责本项目证据范围/医疗条件规则。

验收：指标在0/1/多正例、重复块、K边界、相关文章无关键句、条件被截、scope/工具错误时符合人工算例；工具与实验交给模型的pack一致；旧报告不改名为新口径成功。

### P0-B：修复长度预算，随后校准拒绝

实现位置：`medical/chunking.py`、`schema.py`、`knowledge_base.py`、`bge_reranker.py`，新增 `token_budget.py` / `rerank_policy.py`。

**短期桥接试验**：把512作为候选实验配置，对整套开发/回归和无答案题运行；确认总预算、query保留与实际CPU耗时后，才能决定临时切换。记录截断标记和原文范围。不要只验证三例后直接全量改.env。

**主要策略**：token感知的父子切片。

- 父块保留章节上下文、来源、适用条件；子块用于embedding/重排，初始子块上界试验180/220 tokens。pair总预算试验256/384；实际子块预算必须扣除query、标题与special tokens，不能将这些上界无条件同时使用。
- 完整query先规范：优先保留当前问题，再加入最小必要用户事实。query预算64/96 tokens作为试验值；过长必须显式压缩/切分与记录，不让longest_first任意删除当前问题。
- 标题/章节去重；明确预算包含special tokens。对子块使用可审计的only_second策略；超过预算的子块按完整句/问答/表格单元再拆，不静默丢尾部。
- 每个子块保存parent/section/source版本及原文ranges。命中后按budget展开必要父段/邻句；禁止只向LLM展示脱离条件的剂量、数字或结论。
- 原文偏移可能多段，保存range列表；不能把重叠后重新拼接的文本假装成一个连续原文范围。

**拒绝方案**：先把排序与拒绝拆成两个策略；排序分数用于排次，是否有回答依据由单独gate判断。候选来源资格保持一致，对 ordering_only、现状gate、校准gate 做消融。校准使用独立开发集正例与困难负例，绘制保留正例/过滤负例曲线；候选特征可含top score、margin、dense/lex一致性、覆盖范围，但需消融证明收益。

不设“低分必定拒绝”或“有词法匹配必定救回”的新硬规则；结果可为 `supported / insufficient / unavailable`。低置信资料与确定性来源资格分别表达。LLM每次仍参与，资料不足给一般性解释及清晰追问，不伪造引用。

实验规模控制：先一次改变输入表示；再比较gate；最后比较候选/性能。不要把length×batch×候选×门槛所有组合一起网格搜索。模型微调、更换更大reranker留在稳定基线和足够标签之后。

建议门槛：三个已知回归均恢复关键证据；固定开发/验证中证据召回不低于混合基线，困难负例过滤率不低于90%（暂定研究门槛，正式阈值由规模和误差决定）；关键条件遗漏在标注套件中为0。均属于拟定目标，当前未达成完整验证。

### P0-C：补数据代表性和答案/Agent层评价

1. 保留现有234题原标签。120道新开发题按主题/表达模板分层，增加长追问、双重否定、病史与当前症状、个人事实、混合请求、无依据和相似词干扰。新增80道独立验证题与40道可执行流程题；不要把已暴露80题继续当未见。各类样本量单列，避免重复改写抬总数。
2. 先在常见症状、睡眠、运动和营养中补来源可定位的中文资料。按主题安排新题与资料，不用现有16主题的容易正例代替知识覆盖验收。华佗候选保持隔离。
3. 40流程题以临时SQLite/独立索引执行，覆盖未命中/检索不可用仍有生成请求、记录与更正/跨会话、取消/重试、跨用户拒绝。断言工具和数据库结果，不只判回答里“已记录”。
4. live答案评测调用现有统一LLM配置，记录实际provider/model/prompt hash/request/usage；固定生成设置、限制题数和token预算。初次20题探针，再扩60题正式批次； judge调用预算与生成预算分开。
5. 分别测问题回应、引用ID/URL有效性、引用支持程度、关键条件保留、无资料状态表述、追问质量、任务回执一致性和LLM实际参与。数值词法审计只作辅助。
6. 参考 [Ragas](https://github.com/vibrantlabsai/ragas) 的context recall/faithfulness/relevance与工具评价，建立可选judge adapter，不把整个应用迁移到另一RAG框架。模型判为unsupported/insufficient时保留原判据和分歧；抽样做原文核对，judge不作医学正确性证明。
7. 项目允许模型补充一般健康知识：对明确归因资料的断言评证据支持；对一般知识独立评预期要点与边界；问候、确认和追问不当作事实。不能直接把全回答套入“所有句子须来自RAG”的faithfulness分数，否则和产品目标冲突。

验收：数据按主题聚类报告和paired bootstrap；验证题在定参数前封存，一旦被用于改动就转回归；所有题和错误有分母，unknown/error单列；不能以judge平均分或8/8替代可靠性结论。医疗人员审核继续按用户决定暂缓。

### P1-A：性能与故障预算

实现位置：`bge_reranker.py`、`runtime.py`、`agent/mcp_connection.py`、trace事件与专项bench CLI。

- 先测长度分桶、候选4/6/8、线程1/2/4和batch1/4/8；每个配置相同题/长度分布，至少30个不同问题、每题多次，冷/热/缓存分开。报告P50/P95/P99、置信区间、峰值RSS和正确证据损失。
- 补并发1/2/4与模型worker排队耗时。为单worker设有界队列、排队deadline、任务取消和明确busy/unavailable状态。
- timeout不等于Python后台推理已停：不得超时后并行启动第二个相同forward。未开始任务可撤销，已开始结果可丢弃/不缓存，保持worker生命周期可控。
- 暂定本机热未缓存RAG单并发P95≤2秒；若不能兼顾质量，记录未达标并调整模型/backend，不能靠命中缓存凑分。LLM首token/总响应另立实测基线。
- ONNX/OpenVINO先离线导出/量化和数值对照，再比较真数据质量与CPU/内存。量化改变排序/拒绝结果时必须重新校准，保留PyTorch回退。
- 错误状态、排队和生成连接错误分离；用户始终得到可理解的错误状态，检索故障不冒充未覆盖。

### P1-B：数据发布、追踪与自动验收

- M3建立token策略版本化的staged index、原文/子块manifest、验收后原子active pointer；切换失败继续旧版本；同数量更新时cache也随version失效。
- trace贯穿路由→查询表示→候选→重排→证据pack→生成→健康写入。借鉴 [Langfuse](https://github.com/langfuse/langfuse) 的trace/evaluation关联，先采用本地轻量结构化事件及adapter，避免本机额外常驻基础设施。
- 默认记录IDs/长度/版本/耗时，不记录患者问题和健康正文；合成评測可保存完整输入。原始prompt显式本机调试、owner控制和保留期限单独处理。
- 后端完整锁定依赖与Python版本，保存所有必要tokenizer/config/model资产哈希。发布报告要求相关代码已提交，或提供已审查的源码快照；仅dirty+SHA不足以恢复运行代码。
- CI分离离线合同（每次变更）、真模型固定小回归（显式任务）、收费生成（手动且预算上限）。失败不能发布索引或宣称验收通过；同一数据/版本比较才能产生退化门槛。
- 指标核对、测试套件、正式前端typecheck/build、来源资格、关键证据保留是发布检查。新Windows环境从安装、模型准备到演示的完整复现单独验收。
