# Aide RAG 工程化执行方案

制定日期：2026-10-15。基线提交：`cf76a7f`。本轮状态：方案已建立，以下开发任务尚未执行。

## 1. 目标与完成定义

目标：在现有 Aide 中建立“来源可追溯、检索有证据、回答可核查、性能有预算、变更能回归”的 RAG 闭环，形成可演示、可复现、可用于项目经历的工程成果。

完成后须能回答：这个问题经过了哪些 Agent、检索到了哪些原文、关键依据有没有进入 LLM、模型是否实际参与、工具是否真正完成写入、花费了多少时间和 token、失败后如何恢复。

沿用现有 FastAPI / SQLite / Chroma / BGE / LiteLLM / Agent SDK / React。中文、普通成年人健康科普与就医引导、本机研究；健康事实通过可信工具记录。每轮问答由统一 LLM 参与，RAG 命中、未覆盖和不可用分别表达。医疗人员审核延续已确认的暂缓安排。

文档职责：

- `portfolio-upgrade-plan.md`：整个项目的模块地图。
- `rag-evaluation-engineering-review.md`：原因、实验证据及设计依据。
- **本文件**：下一阶段执行顺序、工作清单和验收关卡。
- `portfolio-progress.md`：实际完成项、测试、提交及剩余问题。

### 阶段1：统一最终证据合同和评测指标（P0）

目的：测量实际交给 LLM 的依据。

工作清单：

- [ ] 1.1 新增 `medical/evidence_contract.py`，统一默认5块、每篇最多2块、内容预算、顺序、来源字段和证据ID生成。
- [ ] 1.2 工具打包与实验共用选择器，记录策略版本、最终pack哈希、chunk/文档数量及截断信息。生成模型token无法精确计算时明确标为估算，并保留API实际usage。
- [ ] 1.3 增加规范原文 `doc_id/version/body_hash/ranges/required_conditions` 标签。先为三例与代表性长短、条件/例外样例建立小型可人工核对集合。
- [ ] 1.3a 旧索引缺少原文ranges时显式标为unmapped；以可验证映射或隔离重建补齐，不能仅凭doc_id或文本相似度算证据覆盖。阶段2继承同一范围合同。
- [ ] 1.4 新增最终证据范围召回、关键条件保留率、候选union/重排池保留率；保留原文档级Recall/MRR/nDCG及旧报告。
- [ ] 1.5 为输入、模型配置、资格、资源和逐题异常生成结构化失败记录，错误计入分母并单列状态。

验收：

1. 相同输入和索引，工具与实验产出的证据pack一致。
2. “命中同一文章但没有关键句”“前5篇与前5块不同”“多个条件只保留一个”均能被测试识别。
3. 无正例/无条件时指标返回空值或明确不适用；不当作满分。
4. 新旧指标版本清晰，基线可重跑。

交付：证据合同、指标/算例测试、第一份证据范围基线。对应原计划 M1a/M5 的补强。

### 阶段2：修复重排输入与配套切片（P0）

工作清单：

- [ ] 2.1 以隔离配置比较256与512，运行开发/回归、困难负例和资源测试；512先作为桥接候选。
- [ ] 2.2 新增 `medical/token_budget.py`，明确query、标题、正文及special tokens预算，保存实际输入长度与截断范围。
- [ ] 2.3 当前问题优先保留，前文仅取必要用户事实；长追问不能因截断只剩旧话题。
- [ ] 2.4 实现token感知父子切片：子块用于检索/重排，父段及必要邻句用于补全回答上下文；保存规范原文范围和parent/section版本。
- [ ] 2.5 标题/章节去重；文章按章节/句子，问答保留问答单元，表格保留表头及行关系；条件、例外和结论共同保留。
- [ ] 2.6 新策略先建隔离索引，比较质量与长度；完成切换及回退准备后才进入运行环境。

初始实验上界：子块180/220 tokens，句对256/384；实际子块长度自动扣除query、标题和special tokens。这些是实验候选，最终参数由结果确定。

验收：三例的关键句进入实际重排输入和最终证据包；已标注的适用条件/例外完整保留；长query、超长句、重叠与跨章节测试通过；完整回归和内存预算通过。此时还不能仅以三例恢复宣称所有问答已改善。

交付：token预算、结构切片、隔离索引和长度/质量对照报告。对应 M3，并修复已确认缺陷。

### 阶段3：补中文资料覆盖与独立题集（P0/P1）

工作清单：

- [ ] 3.1 围绕常见症状、睡眠、运动、营养建立coverage backlog，记录“没有资料/资料不完整/已有但未召回”。
- [ ] 3.2 逐主题采集中文权威原文，按现有规则目录存D盘，保存raw/normalized/hash/定位/适用范围；华佗候选继续隔离。
- [ ] 3.3 新建约120道开发题、80道独立验证题、40个可执行流程；数量是规划值，按主题和难度披露实际完成数。
- [ ] 3.4 区分单问、长追问、否定/历史叙述、多事实、困难负例和紧急表述；每题有原文范围或明确无依据标签。
- [ ] 3.5 按题目家族/模板管理划分，审查重复与相似表达。共享检索corpus正常；新主题/新来源泛化另设子组。
- [ ] 3.6 验证集在定参数前封存；被用于修复或调参的样例转回归，另补未见表达。

建议分布可在正式封存前调整：

| 组 | supported | unanswerable | followup | urgent | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 新开发题 | 60 | 40 | 12 | 8 | 120 |
| 新独立验证题 | 40 | 24 | 8 | 8 | 80 |

正常/紧急期望是额外标签，正常反例不能全部归为无答案；答案本身有权威资料时仍标supported。

40个流程按offline/fault/live标记，覆盖健康记录与更正、跨会话、跨用户、工具错误、未命中仍生成、复合意图、取消/重复执行与日历刷新。模拟故障和真实模型结果分别报告。

验收：新增资料可定位/资格通过；旧集保留；题集规范/标签/重复检查通过；每次扩容都有覆盖报告。按主题聚类统计，点估计与误差一起呈现。

交付：版本化中文资料、开发/验证/流程清单和覆盖报告。对应 M1b/M3。

### 阶段4：校准排序和依据充分性判断（P1）

- [ ] 4.1 新增 `medical/rerank_policy.py`，排序与依据充分性判断分别实现；来源资格检查独立保留。
- [ ] 4.2 使用相同候选集合比较融合排序、只重排次序、当前过滤、校准策略，定位每一阶段的得失。
- [ ] 4.3 在开发集选择分数/margin/召回一致性等特征及门槛，控制实验数量，保存正例保留与困难负例过滤曲线。
- [ ] 4.4 参数确定后运行独立验证，保留逐题胜负、分主题指标和paired bootstrap；不根据同一验证结果反复调参数。

建议发布门槛：新证据召回不低于相同条件下的融合基线；困难负例过滤率至少90%；已标注关键条件回归失败为0。小样本区间和不确定性必须展示，正式门槛在首次打开新验证结果前确定。

交付：可解释的策略选择和对照报告。达不到门槛时保留旧策略，候选作为研究配置；不能通过改标签或放宽统计口径宣称通过。

### 阶段5：验证最终答案与Agent任务（P1）

- [ ] 5.1 通过现有统一LLM配置运行20题探针，检查实际生成请求、usage、引用和状态；再开展约60题答案批次，分别设置生成与judge预算。
- [ ] 5.2 对问题回应、引用有效性/支持程度、关键条件、资料状态表述、追问和任务回执评分。
- [ ] 5.3 增加可选judge adapter，参照已调研Ragas指标；保留判据/分歧和抽样原文核对。模型judge只作辅助证据。
- [ ] 5.4 资料归因断言检查原文支持；一般健康知识按允许范围和预期要点单独评价；确认/追问不作为事实断言。
- [ ] 5.5 执行40流程，至少选择12项代表性流程验证真实模型参与；offline/mocked不能算作真实生成验收。
- [ ] 5.6 合成用户/临时数据库核查真实工具调用、日期、幂等、更新、权限和持久化，不以“回答说成功”作为写入证据。

硬性关卡：未命中/不可用仍产生真实生成请求；引用ID/来源可核对；记录确认与工具回执一致；跨用户访问拒绝；全部失败显式保留。答案质量分项报告，不能用一个平均分遮盖严重错误。

### 阶段6：性能、索引发布与自动验收（P1/P2）

- [ ] 6.1 至少30个不同问题，配置交错运行、每题重复，分别测冷启动/热未缓存/缓存、并发1/2/4，记录分位数、排队和峰值RSS。
- [ ] 6.2 单独比较候选4/6/8、batch1/4/8、线程1/2/4；需要时再试ONNX/OpenVINO，重新核对质量与数值变化。
- [ ] 6.3 推理worker有界排队、deadline和取消；超时不得重复开启同一forward。检索错误、排队超时和模型连接失败分别呈现。
- [ ] 6.4 完成staged index→验收→原子active pointer，失败继续旧版本；缓存包含内容/索引版本，覆盖同数量更新与回滚。
- [ ] 6.5 贯穿请求的trace关联路由、检索、证据包、生成和写入；默认记录ID、版本和运行指标。
- [ ] 6.6 锁定后端依赖、Python和模型/tokenizer/config资产；报告关联可恢复代码版本。

拟定性能目标：本机单并发、热未缓存RAG P95≤2秒；LLM首token与总回答另测。若资源下无法兼顾质量与耗时，明确记录未达标并选择后端/模型方案，不使用缓存统计替代未缓存性能。

交付：性能及真实故障矩阵、索引发布/回退、CI、复现说明和演示材料。对应 M4/M5/M6。

## 4. 每轮工作规则

1. 开始读取本清单和进度、检查分支与改动；完成一个有验收边界的任务后更新状态。
2. 默认隔离索引和合成用户。涉及用户数据迁移时先备份，再验证恢复路径。
3. 每次报告保存代码/数据/模型/参数/输入合同版本、运行条件、错误与逐题结果。归档失败，不覆盖首次报告。
4. 小提交、明确回退点；延续用户已授权的版本控制/推送，只提交本轮文件。索引回退与Git回退分别处理。
5. 每阶段交付：改了什么、测试命令/结果、指标分母、限制、提交号。通过可控测试与实际流程分别表述。

## 5. 首个开发包

先执行 **1.1～1.5**：统一证据包 → 原文范围标签 → 算例/合同测试 → 真实BGE证据范围基线。

第一包完成后，用户应能检查：一个问题交给LLM的具体依据、依据原文位置、是否发生截断，以及为什么算命中或漏召回。随后进入阶段2修复输入与切片。

## 6. 总体验收

- [ ] 原文→切片→重排→最终证据→回答能够逐项追踪。
- [ ] 固定数据和配置可以重跑，旧/新口径和真实/模拟结果区分清楚。
- [ ] 质量门槛在验证前确定，失败会阻止策略/索引发布。
- [ ] 已知三例、关键条件、长追问、困难负例和用户数据隔离通过专项验收。
- [ ] 答案与任务有真实LLM/工具/数据库证据。
- [ ] 本机资源下的性能、故障恢复、CI和新环境复现有报告。
- [ ] 演示与项目经历中的每个数字都能追溯到报告和适用边界。
